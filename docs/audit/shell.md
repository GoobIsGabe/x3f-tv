Facts that matter:

* **Both build types are signed with the same committed debug keystore.** That is deliberate
  (`HANDOFF.md`: "stable signing means it updates in place"). It also means anyone with the repo can
  produce a signature-matching APK.
* **CI ships `assembleDebug`** (`.github/workflows/build.yml`, step "Build debug APK" →
  `cp app/build/outputs/apk/debug/app-debug.apk x3f-tv.apk`). The APK users install is a *debug*
  build: `debuggable=true`, no minification, WebView devtools available over `adb`.
* `version.txt` on the `dist` branch is generated by
  `grep -m1 versionCode app/build.gradle | grep -o '[0-9]\+'` — i.e. it is literally
  `versionCode`, and the updater compares it to `BuildConfig.VERSION_CODE`.
* `lint { abortOnError false }` means the Android lint checks that would flag several of the
  defects below (e.g. `SetJavaScriptEnabled`, `MissingPermission`, `JavascriptInterface`) never fail
  a build.

**Wire formats.**

| Characteristic | UUID | Properties used | Payload |
|---|---|---|---|
| Force | `e3458901-…` | NOTIFY (CCCD written at `:311`) | 8 bytes, **float64 little-endian** (`:347`) |
| Battery | `e3458902-…` | NOTIFY if present, else READ (`:365`, `:387`) | 2 bytes, **uint16 little-endian, cell millivolts** (`:404`) |

The millivolt → percent map lives *in JavaScript*, not Java: `launcher.html:216`
`const pct=Math.max(0,Math.min(100,Math.round((mv-3300)/900*100)));` — i.e. 3300 mV = 0 %,
4200 mV = 100 %. Java only range-checks `1 … 10000` (`:405`).

## 1.5 Lifecycle

`onCreate` (`:98-114`):

1. `FLAG_KEEP_SCREEN_ON`
2. open `SharedPreferences("x3f", MODE_PRIVATE)`
3. `buildWeb()` — construct + `setContentView` + `loadUrl(LAUNCHER)`
4. register `dlRx` for `DownloadManager.ACTION_DOWNLOAD_COMPLETE` (`RECEIVER_EXPORTED` on SDK ≥ 33)
5. get the `BluetoothAdapter`; if null → `setBar("", "No Bluetooth")` and **return** (no WebView bar update path afterwards)
6. if adapter disabled → `setBar("wait", "Turn on Bluetooth")` and *fall through*
7. `ensurePermsThenScan()`

`onDestroy` (`:572-577`): `stopScan(); closeGatt(); unregisterReceiver(dlRx); web.destroy(); web = null;`

**There is no `onPause`, `onResume`, `onStop`, `onNewIntent`, `onSaveInstanceState`, or
`onRestoreInstanceState`.** The WebView is never paused, its timers are never paused, and the BLE
scan/connection is never suspended.

# 3. Defects

Severity key: **S1** breaks the product for a real user; **S2** wrong behaviour with a workaround;
**S3** latent / robustness / hygiene.

## 3.1 Threading and memory model

### D-01 (S1) — Every piece of shared state is a non-volatile field mutated from up to four threads

**Evidence.** `MainActivity.java:77` `private boolean scanning = false, connecting = false, connected = false;`
and `:83 webReady`, `:80 haveBaseline`, `:79 baseline`, `:93 watchdog`, `:95 battPoll`, `:96 overlayOpen`,
`:87 barState/barText`. None declared `volatile`; no `synchronized` block anywhere except around
`seen` (`:260`, `:454`, `:469`).

Writers/readers:
* `connecting`/`connected` — written on the binder thread (`:280` inside `connectTo` called from
  `scanCb.onScanResult` `:269`; `:297`, `:305`, `:312`), read on the UI thread (`:237`, `:285`,
  `:394`) and on the binder thread.
* `haveBaseline` — written on the **JavaBridge** thread (`:427 reZero`), written and read on the
  **binder** thread (`:348`).
* `overlayOpen` — written on the JavaBridge thread (`:446`), read on the UI thread (`:554`).
* `webReady` — written on the UI thread (`:132`), read on the binder thread (`:352`) and the UI
  thread.
* `watchdog` / `battPoll` — `long` fields incremented from the binder thread (`:298`, `:323→:392`)
  and compared on the UI thread (`:228`, `:394`). **A `long` write is not guaranteed atomic** for
  non-volatile fields (JLS 17.7).

**Failure scenario.** User presses "Re-Zero" in Nova. `Bridge.reZero()` sets `haveBaseline=false`
on the JavaBridge thread. The BLE binder thread is spinning in `handleForce` at ~100 Hz with
`haveBaseline` hoisted into a register by the JIT; it never observes the write. The Re-Zero button
does nothing, forever, with no error. The user's only recovery is to leave the game (which does not
help — `haveBaseline` is only reset in `onServicesDiscovered` `:312`) or restart the app.

### D-02 (S1) — `connectTo` has a check-then-act race that can leak GATT client interfaces

**Evidence.**

```java
// :269  (binder thread, ScanCallback)

// :278-283

    if (connecting || connected) return;
    connecting = true; targetAddress = d.getAddress(); stopScan(); setBar("wait", "Connecting…");
    try { gatt = d.connectGatt(this, false, gattCb, BluetoothDevice.TRANSPORT_LE); }
    ...
}
```

`connectTo` does not `closeGatt()` first, and the guard is a plain read of a plain field.

**Failure scenario.** Two `onScanResult` callbacks for the same bar (one from the advert, one from
the scan response) are delivered close together. Both pass `!connecting`. Both call `connectGatt`.
The second assignment overwrites `gatt`, so the first `BluetoothGatt` is never `close()`d — its
client interface stays registered in the Bluetooth stack. Android allows a hard limit of GATT
client registrations per process; repeated reconnect cycles leak one each time until
`connectGatt` starts returning `null` and BLE stops working for the whole app until it is
force-stopped.

### D-03 (S2) — `injectForce` can NPE after `onDestroy`

**Evidence.** `:352` `if (!webReady || web == null) return;` then `:356`
`web.post(() -> { … });`. `web` is nulled on the UI thread at `:576`. Between the null check on the
binder thread and the `web.post` on the next line, the UI thread can run `onDestroy`.

**Failure scenario.** The user backs out of the app (or the system recreates the activity for a
`uiMode` change) while the bar is streaming. `handleForce` fires between the check and the post →
`NullPointerException` on a Binder thread → process crash.

## 3.2 BLE connection lifecycle

### D-04 (S1) — `reconnect()` arms no watchdog and uses `autoConnect=true`, so the app can get permanently stuck on "Reconnecting…"

**Evidence.**

No `armWatchdog()` here (unlike `tryKnownDevices` `:197/:206/:214` and `Bridge.pickDevice` `:439`).

**Failure scenario.** The bar sleeps mid-workout. `onConnectionStateChange(DISCONNECTED)` fires →

answers. `connecting` stays `true` forever, which makes `startScan()` return immediately at `:237`,
so no scan ever runs. The chip says "Reconnecting…" indefinitely. The only recovery is
`X3F.rescan()` — reachable, but only if the user knows to open the bar chip → Scan again. Restarting
the app is what most people will do.

### D-05 (S1) — The force baseline is a single sample, taken at the worst possible moment

**Evidence.** `:345-350`

```java
private void handleForce(byte[] v) {
    if (v == null || v.length < 8) return;
    double rawd = ByteBuffer.wrap(v).order(ByteOrder.LITTLE_ENDIAN).getDouble();
    if (!haveBaseline) { baseline = rawd; haveBaseline = true; }
    injectForce(Math.max(0, rawd - baseline));

```

The web build averages a 1.5-second window (`startTare()` at e.g. `nova.html:160`, consumed in
`onSample()` `:162`). The shell takes the *first packet*.

**Failure scenario.** `launcher.html:231` literally tells the user to "wake the bar (load a band)".
A bar that only starts notifying under load therefore delivers its first packet **while loaded**.
That value becomes the baseline. Every subsequent reading is `max(0, raw − loaded_baseline)` = 0
until the user pulls harder than the accidental baseline. The meter reads 0 and the bar looks
broken. `HANDOFF.md` even documents the inverse hazard ("Zeroing while already in the start position
bakes that load into the baseline") without noting that the *automatic* baseline has exactly the
same failure.

### D-06 (S2) — Peak force is systematically under-reported because the injection throttle drops samples

**Evidence.** `:353-354`

```java
long now = SystemClock.uptimeMillis();

```

The dropped sample is discarded, not folded into a running max.

**Failure scenario.** The bar notifies at ~100 Hz; the shell forwards ~62 Hz of *instantaneous*
values, throwing away ~38 % of packets. A fast concentric snap's true peak lands in a discarded
packet. The web build's `onSample()` sees every packet. Consequences: `x3f-set.js`'s peak
measurement is low on TV, `X3FCal.observe()` auto-learns a ceiling that is too low, PBs are wrong,
and TV-logged history is not comparable with phone-logged history. For an app whose product is
measuring force, this is a correctness bug, not a perf trade-off. The fix is one line: track
`pendingMax` between injections.

### D-07 (S2) — Bluetooth-off and Location-off are dead ends with no recovery

**Evidence.**
* `:112` `if (!adapter.isEnabled()) setBar("wait", "Turn on Bluetooth");` then falls through to
  `ensurePermsThenScan()` → `startScan()` → `:241` `if (scanner == null) { setBar("wait", "Bluetooth off"); return; }`.
* There is **no** `BluetoothAdapter.ACTION_STATE_CHANGED` receiver anywhere in the file, and no
  `ACTION_REQUEST_ENABLE` intent.
* There is **no** `LocationManager.isLocationEnabled()` check, although on API ≤ 30 BLE scanning
  silently returns zero results when Location Services are off (the manifest requests
  `ACCESS_FINE_LOCATION` with `maxSdkVersion="30"` at `:15`, so this path is live for minSdk 24
  through 30).

**Failure scenarios.**
1. TV boots with Bluetooth off. The app shows "Bluetooth off". The user turns Bluetooth on in
   system settings and comes back — the app never notices and keeps saying "Bluetooth off" until
   restarted or until the user finds Scan again.
2. Android 11 TV box with Location Services off. `startScan()` succeeds, `onScanFailed` is never
   called, no results ever arrive. The UI sits on "Scanning for bar…" forever with no explanation.

### D-08 (S2) — "No force channel" is a terminal state

**Evidence.** `:307` `if (ch == null) { setBar("", "No force channel"); return; }` — `connecting`
stays `true`, `connected` stays `false`, no `closeGatt()`, no retry, no watchdog.

**Failure scenario.** The bar's GATT cache in Android is stale (a firmware update changed the
characteristic set, or discovery raced) so `CH_FORCE` is missing. The app is now permanently wedged:
`connecting == true` blocks `startScan()` (`:237`) and `reconnect()` (`:285`) for the rest of the
process's life. Only "Scan again" recovers.

### D-09 (S2) — `onServicesDiscovered` and `onConnectionStateChange` ignore `status`

**Evidence.** `:294` `public void onConnectionStateChange(BluetoothGatt g, int status, int newState)`
and `:303` `public void onServicesDiscovered(BluetoothGatt g, int status)` — neither method body
mentions `status`.

**Failure scenario.** A GATT_ERROR (133) connect produces `status=133, newState=STATE_CONNECTED` on
some stacks; `discoverServices()` on that handle fails, `onServicesDiscovered` is never called, and
the shell sits on "Connected…" indefinitely with no watchdog (the watchdog only guards the direct-
connect path and only for 9 s, after which it has already fired and given up). Likewise a failed
service discovery is reported to the user as "Wrong device — scanning…", which blames the hardware
for a stack error and throws away a good connection.

### D-10 (S3) — The scan is unfiltered, low-latency, and never stopped

**Evidence.** `:242-245`

running. `X3F.rescan()` can also trip Android's `SCAN_FAILED_SCANNING_TOO_FREQUENTLY` (5 starts in
30 s) which surfaces as the generic "Scan failed" (`:271`).

### D-11 (S3) — `seen` grows without bound and re-serialises the whole map per new device

**Evidence.** `:258-267` adds every address ever seen; `:466-483 pushDevices()` rebuilds the entire

unnavigable wall of `(unnamed device)` chips, and each new advert triggers a full re-serialise +
JS eval on the UI thread while a game is running.

**Evidence.** `:467` `if (web == null || !webReady) return;` — `pushDevices` bails silently. The
only replay on `onPageFinished` is `pushBar()` and `pushBattery()` (`:135-136`); `pushDevices()`

**Failure scenarios.**
1. Cold start. The scan finds the bar's advert in the first 300 ms, before `onPageFinished`. The
   name doesn't match and there's no service UUID, so it isn't auto-connected. The user opens the
   picker: "Nothing seen yet — wake the bar…". The device is in `seen` but will never be pushed
   because it is no longer "new".
2. Play a game, press Back to the launcher. `onPageFinished` fires, bar + battery are replayed, the
   device list is not. The picker is empty even though `seen` has entries.

### D-13 (S3) — Battery only understands a 2-byte payload

**Evidence.** `:403` `if (v == null || v.length < 2) return;`

**Failure scenario.** A bar (or firmware revision) that exposes the standard Battery Level format
(single byte, 0–100 %) on `e3458902-…` is silently ignored; the chip shows no percentage and there
is no log line to explain it.

### D-14 (S3) — No connection-priority or MTU negotiation

**Evidence.** `gatt.requestConnectionPriority(...)` and `gatt.requestMtu(...)` appear nowhere in
the file. After `onServicesDiscovered` (`:303-317`) the shell only writes the CCCD.

**Consequence.** Android's default LE connection interval is 30–50 ms. A bar notifying faster than
that will have packets queued and coalesced by the controller, adding tens of milliseconds of
latency and jitter between a pull and the on-screen response — the single thing a force game cannot
tolerate. `CONNECTION_PRIORITY_HIGH` requests 11.25–15 ms.

## 3.3 Activity / WebView lifecycle

### D-15 (S1) — The app never pauses: Back leaves the games running at full tilt in the background

**Evidence.** `:557` `else if (isLauncher(currentUrl)) { moveTaskToBack(true); }`. There is no
`onPause`/`onStop` override in the file, so `web.onPause()`, `web.pauseTimers()`, `stopScan()` and
`gatt.disconnect()` are never called.

**Failure scenario.** The user presses Back on the launcher to watch TV. The task is backgrounded
but the process keeps: a `SCAN_MODE_LOW_LATENCY` BLE scan, a live GATT connection with 100 Hz
notifications, a 16 ms `setInterval` in the WebView, `X3FFX`'s `requestAnimationFrame` ambience,
and — if a game was showing — its whole canvas render loop. `FLAG_KEEP_SCREEN_ON` is a window flag
so the screen does release, but the CPU/GPU work does not stop until the system kills the process.
On a low-end TV stick this is visible as the *other* app stuttering.

### D-16 (S2) — `configChanges` is too narrow: a `uiMode` change destroys the running game

**Evidence.** `AndroidManifest.xml:33`
`android:configChanges="orientation|screenSize|keyboardHidden"`. Missing: `uiMode`, `density`,
`fontScale`, `smallestScreenSize`, `screenLayout`, `layoutDirection`, `navigation`, `touchscreen`,
`colorMode`.

**Failure scenario.** A Google TV switching between day and night mode, an HDMI resolution change, or
a system display-size change recreates the activity mid-set. `onDestroy` runs, the WebView is
destroyed and rebuilt at `LAUNCHER` (`:144` — there is no `onSaveInstanceState`/`currentUrl`
restore), the GATT connection is closed, and the user's in-progress Nova run and unlogged set are
gone.

### D-17 (S2) — `webReady` is never cleared, so Back during a page load backgrounds the app

**Evidence.** `webReady = true` at `:132` inside `onPageFinished`; there is no `onPageStarted`
override and no place that sets it back to `false`. `currentUrl` is likewise only updated at
`:131`.

**Failure scenario.** The user picks Nova, the launcher starts fading out (`X3FFX.leave` waits
190 ms, `x3f-fx.js:218-222`), and the user immediately presses Back because they picked the wrong
card. `currentUrl` is still `launcher.html`, so `isLauncher(currentUrl)` is true, so
`moveTaskToBack(true)` runs and the whole app drops to the TV home screen — while Nova continues
loading behind it.

### D-18 (S3) — `web.destroy()` is called while the WebView is still the content view

**Evidence.** `:576` `if (web != null) { web.destroy(); web = null; }` with no
`((ViewGroup) web.getParent()).removeView(web)` first. The platform documentation requires removal
from the view hierarchy before `destroy()`.

**Consequence.** Undefined behaviour in the WebView's teardown path; in practice a leaked native
surface or a crash on some OEM WebView builds.

### D-19 (S3) — Posted runnables outlive the activity

**Evidence.** `ui.postDelayed(MainActivity.this::reconnect, 1200)` (`:300`),
`ui.postDelayed(MainActivity.this::startScan, 800)` (`:305`), the anonymous `Runnable`s in
`armWatchdog` (`:226`) and `armBattPoll` (`:393`). `onDestroy` (`:572-577`) never calls
`ui.removeCallbacksAndMessages(null)`.

**Consequence.** Each one holds a strong reference to a destroyed `MainActivity` (and, transitively,
to the destroyed WebView). `armBattPoll` re-arms itself every 5 minutes indefinitely, so a single
recreation leaks the whole activity graph permanently.

### D-20 (S2) — Back from a game does `loadUrl`, not `goBack`

**Evidence.** `:557` `else { web.loadUrl(LAUNCHER); }`

**Consequence.** A full reload of `launcher.html` every time: re-parse 18 KB, re-run
`x3f-exercises.js` + `x3f-progress.js` + `x3f-music.js` + `x3f-fx.js` + `x3f-nav.js`, re-mount the
ambient canvas, re-request the Google Fonts stylesheet. On a cheap TV that is a visible stall on
every exit. It also grows the back-forward list without bound over a session; the games' own back
button (`nova.html:65`) uses `history.back()`, so the two mechanisms interleave.

## 3.4 Input

### D-21 (S1) — Key auto-repeat is not filtered, so holding a direction sprays the focus

**Evidence.** `:544` `if (webReady && e.getAction() == KeyEvent.ACTION_DOWN)` — `getRepeatCount()`
is never read.

**Failure scenario.** The user holds Right on the remote to move across the launcher's 11-card grid.
Android's key auto-repeat delivers `ACTION_DOWN` events at the system repeat rate (typically 50 ms
after a 400 ms delay), so `__x3fNav('right')` runs ~20×/s. The cursor blows past the target and
wraps. Every TV UI rate-limits or accelerates D-pad repeat; this one does neither.

### D-22 (S1) — `KEYCODE_ENTER` is swallowed unconditionally, so text inputs are unusable

**Evidence.** `:550-552` maps `DPAD_CENTER`, `ENTER` and `BUTTON_A` to `nav("enter")` and
returns `true` with no check on what is focused.

**Failure scenario.** Arena has two number inputs — `arena.html:139`
`<input type="number" id="bandMaxInp">` and `:143` `<input type="number" id="calW" value="25">`.
The BOOTSTRAP's `items()` selector includes `input` (`:640`), so the D-pad *can* focus them, and
`nav('enter')` calls `cur.click()` on them (`:647`), which does not open the IME. Every key that
would type is either swallowed (`ENTER`) or delivered to a WebView that has no soft keyboard shown.
Arena's "hang a known weight and calibrate" and "max units on this band" features are unreachable on
TV — silently, because the controls look focusable.

### D-23 (S2) — Back never closes a game's overlay, because only the launcher reports overlay state

**Evidence.** `:554` `if (overlayOpen) { … }`. `overlayOpen` is only ever set `true` from
`launcher.html:248` (`X3F.setOverlay(!!on)` inside `showFinder`). No game calls
`X3F.setOverlay`. `:133` resets it to `false` on every page load.

**Failure scenario.** In Nova, clear a sector → the Upgrade Bay opens (`nova.html:92`
`<div class="scrim" id="shop">`). Press Back to close it. `overlayOpen` is `false`, `currentUrl` is
`nova.html` → `web.loadUrl(LAUNCHER)`. The run is destroyed and the stardust is gone. Same for
Nova's `#gameover`, Arena's sheets, and every `.scrim` in every game.

### D-24 (S3) — Missing keycodes for common remotes and controllers

**Evidence.** the switch at `:545-559`.

`KEYCODE_BUTTON_B` (the natural "back" on a gamepad) falls through to `super.dispatchKeyEvent`,
where nothing handles it. `KEYCODE_NUMPAD_ENTER`, `KEYCODE_ESCAPE`, the four diagonal
`KEYCODE_DPAD_*_*` codes and `KEYCODE_MENU` are likewise unhandled. `x3f-nav.js` has a gamepad pump
(`:246-271`) but it is only loaded on the launcher and the three menu pages — the games have no
gamepad support at all under the shell.

### D-25 (S3) — `nav()` and the Back branch access `web` inconsistently

**Evidence.** `:541` `private void nav(String dir) { if (web != null) web.evaluateJavascript(...); }`
guards; `:556` `web.evaluateJavascript("window.__x3fCloseOverlay&&…")` does not.

## 3.5 JS bridge and injection safety

### D-26 (S1, security) — A BLE device name reaches `innerHTML` in a page that holds the Java bridge

**Evidence.** Chain:

1. `:275` `n = r.getScanRecord().getDeviceName()` — attacker-controlled, straight off the radio.
2. `:262` `seen.put(addr, name != null ? name : "(unnamed device)")`.
3. `:474-475` `.append(jsSafe(e.getValue()))` — `jsSafe` (`:461-465`) strips only
   `\`, `"`, `'`, `\n`, `\r`. It does **not** strip `<`, `>`, `&`, backtick, or `=`.
4. `:479` `"window.__x3fDevices&&window.__x3fDevices(" + sb + ")"`.
5. `launcher.html:236` `b.innerHTML=(d.n||'(unnamed)')+'<small>'+d.a+'</small>';`

**Failure scenario.** A nearby device advertises the Complete Local Name
`<img src=x onerror=X3F.checkUpdate()>` (37 bytes — fits in a scan response). The user opens the bar
picker. The payload executes in the `file://` origin of `launcher.html`, which has
`window.X3F` bound (`:124`). It can call `X3F.checkUpdate()` (kick off an APK download and pop the
system installer), `X3F.pickDevice(<attacker MAC>)` (redirect the app onto the attacker's fake bar
and feed arbitrary force values into the user's logged history), `X3F.rescan()`,
`X3F.setOverlay(true)` (permanently break the Back button), and read/write every `x3f_*`
localStorage key — the user's entire training history.

**Fix direction.** Escape at the sink (`textContent` + a separate `<small>` element), *and* pass
device names as a real JSON payload built with `org.json.JSONArray` instead of string concatenation.

### D-27 (S2, security) — The bridge is attached to any URL the WebView can reach

**Evidence.** `:124` `web.addJavascriptInterface(new Bridge(), "X3F")` with no
`shouldOverrideUrlLoading` override anywhere in the `WebViewClient` (`:129-142`). With a
`WebViewClient` set and no override, the WebView loads *every* navigation in place, including
`http(s)`.

**Failure scenario.** Today no bundled page links off-site (verified: no `href="http…"` outside the
Google Fonts `<link>` tags). But the moment one does — or the moment a page is compromised via D-26
and calls `location.href='https://…'` — that remote page inherits `window.X3F`. There is no origin
allowlist and no `@JavascriptInterface` origin check.

### D-28 (S3) — `checkUpdate()` spawns an unbounded number of threads and downloads

**Evidence.** `:428` `public void checkUpdate() { new Thread(MainActivity.this::doCheckUpdate).start(); }`
— no guard flag, no debounce, no executor.

**Failure scenario.** The remote's OK key repeats (see D-21) on the "⟳ Check for updates" button.
Ten `doCheckUpdate` threads run, ten `DownloadManager` requests are enqueued to the *same*
destination file (`:519`), `dlId` (`:520`) is overwritten by each, and `dlRx` (`:526`) only matches
the last one. The other nine downloads finish silently and orphan.

### D-29 (S3) — Three inconsistent JS-escaping policies

**Evidence.** `pushBar` `:421` (`'` only, `barState` not escaped at all), `pushUpdate` `:486`
(`'` only), `pushDevices` `:474` (`jsSafe`), `onPageFinished` `:137`
(`BuildConfig.VERSION_NAME` interpolated raw). All of these are safe *today* only because every
value except a device name is a compile-time literal. Any future dynamic string — a firmware
version, a device name in a status message, a localised string — becomes an injection.

## 3.6 Updater

### D-30 (S2) — `httpGet` ignores the response code and leaks the stream

**Evidence.** `:504-510`

```java
private String httpGet(String u) throws Exception {
    HttpURLConnection c = (HttpURLConnection) new URL(u).openConnection();
    c.setConnectTimeout(9000); c.setReadTimeout(9000); c.setRequestProperty("User-Agent", "x3f-tv");
    InputStream in = c.getInputStream(); ByteArrayOutputStream bo = new ByteArrayOutputStream();
    byte[] b = new byte[4096]; int n; while ((n = in.read(b)) > 0) bo.write(b, 0, n);
    in.close(); c.disconnect(); return bo.toString("UTF-8").trim();
}
```

No `getResponseCode()`, no `try/finally` (a mid-read `IOException` leaks the socket), no
`Cache-Control: no-cache` header.

**Failure scenario.** `raw.githubusercontent.com` serves cached content with a ~5-minute TTL. Right
after a CI publish, the TV reads a stale `version.txt` and reports "You're on the latest" — exactly
the symptom `DEPLOY.md` warns about, but from a second, undocumented cause.

Also `while ((n = in.read(b)) > 0)` terminates on a legitimate `read()` returning 0, which a socket
stream may do. `!= -1` is the correct condition.

### D-31 (S2) — The updater keys on `versionCode`, but the payload that changes is the asset bundle

**Evidence.** `:494` `if (remote <= BuildConfig.VERSION_CODE) { pushUpdate("You're on the latest…"); return; }`
and `.github/workflows/build.yml` deriving `version.txt` from `versionCode` in `app/build.gradle`.

**Failure scenario.** A developer edits a game in `web/`, runs `sync-from-web.py`, and pushes without
bumping `versionCode` (documented as a known trap in `DEPLOY.md` step 3 and `HANDOFF.md`). CI builds
and publishes a genuinely different APK, `version.txt` is unchanged, and every TV in the field
reports "You're on the latest". The build system has all the information needed to key on the git SHA
or an asset hash and does not use it.

### D-32 (S3) — Nothing verifies what was downloaded

**Evidence.** `:511-522` enqueues `APK_URL`; `:523-538` opens whatever landed with `ACTION_VIEW`.
There is no size check, no hash check, no `PackageManager.getPackageArchiveInfo` versionCode check
against `remote`, and no check that the signature matches.

**Failure scenario.** The `latest` release asset is stale relative to `dist/version.txt` (the release
upload step failed, or the release was re-tagged). The user downloads the *same* version they have,
the installer says "no changes", and "Check for updates" will offer it again every time.

### D-33 (S3) — The download-complete receiver only lives as long as the activity

**Evidence.** registered in `onCreate` `:104-108`, unregistered in `onDestroy` `:575`.

**Failure scenario.** A slow download on a weak Wi-Fi. The user presses Back on the launcher →
`moveTaskToBack(true)` (`:557`) → the system later kills the process. The APK finishes downloading
into `Android/data/com.goob.x3ftv/files/Download/x3f-update.apk`; nothing ever opens the installer,
and nothing tells the user. Re-opening the app and pressing Check for updates re-downloads from
scratch (`:513` deletes the file first).

### D-34 (S3) — `startActivity` for the unknown-sources settings screen runs off the UI thread

**Evidence.** `:495-498` runs inside `doCheckUpdate`, which is on the ad-hoc thread created at
`:428`. `getPackageManager().canRequestPackageInstalls()` and `startActivity` are both called there.

### D-35 (S3) — `Integer.parseInt` on scrubbed remote text

**Evidence.** `:491-493`
`String s = httpGet(VERSION_URL).replaceAll("[^0-9]", ""); … int remote = Integer.parseInt(s);`

**Failure scenario.** GitHub returns an HTML error/rate-limit page. Every digit in it is
concatenated into one number, which overflows `int` → `NumberFormatException` → the generic
"Update check failed". The user has no idea whether they are up to date.

## 3.7 Rendering / page-load

### D-36 (S1) — Every bundled page render-blocks on a Google Fonts request

**Evidence.** All 13 bundled HTML files carry a network stylesheet. E.g.
`launcher.html:10-11`:

```html
<link rel="preconnect" href="https://fonts.googleapis.com">
<link rel="preconnect" href="https://fonts.gstatic.com" crossorigin>
<link href="https://fonts.googleapis.com/css2?family=Fredoka:wght@500;600;700&family=Space+Grotesk:wght@500;700&display=swap" rel="stylesheet">
```

Confirmed present in `arena, bloom, calibrate, duel, flow, index, launcher, library, nova, progress,
rhythm, routine, splash`. The shell sets no `setCacheMode` (`:119-121`), so on a cold start with no
cache the WebView must resolve DNS, do a TLS handshake and fetch the stylesheet before first paint.

**Failure scenario.** The TV is offline (or the Wi-Fi has not associated yet at boot, which is the
normal case for "turn on TV → open app"). The launcher shows **nothing** — not even the dark
background beyond `web.setBackgroundColor` — until the network stack gives up. `HANDOFF.md` claims
"the whole APK is under 5MB and must work offline"; it does not.

### D-37 (S2) — The window background does not match the app, so cold start flashes

**Evidence.** `web.setBackgroundColor(0xFF05030F)` at `:123` styles the *WebView*.
`AndroidManifest.xml:29` uses `@android:style/Theme.DeviceDefault.NoActionBar` with no
`android:windowBackground` override and no custom theme in `res/values/`
(`res/values/` contains only `strings.xml`).

**Failure scenario.** Launching from the leanback launcher paints the DeviceDefault window
background (light grey on many OEM TV builds) for the duration of the activity's startup, then the
WebView's near-black, then the page. A visible white flash on every launch.

### D-38 (S2) — A renderer crash kills the app

**Evidence.** `WebViewClient` at `:129-142` overrides only `onPageFinished`. No
`onRenderProcessGone`. On API ≥ 26, if `onRenderProcessGone` is not overridden (or returns
`false`), the framework kills the app process when the renderer dies.

**Failure scenario.** A long Nova session on a 1 GB TV stick; the renderer is OOM-killed. The app
disappears from the screen with no message. The correct handling — return `true`, tear down the dead
WebView, build a new one, reload the last URL — is not implemented.

### D-39 (S2) — Load errors show the raw Chromium error page

**Evidence.** No `onReceivedError` / `onReceivedHttpError` override.

**Failure scenario, and it is live today.** `library.html:57`, `progress.html:107` and
`routine.html:145` all declare
`window.X3FFILES = { …, ascent:'ascent.html' }` (injected by `tools/sync-from-web.py`'s `TV_BLOCK`),
and `x3f-exercises.js:120` lists Ascent as a game — but **`app/src/main/assets/ascent.html` does not
exist** (`X3F_Ascent.html` is not in `sync-from-web.py`'s `GAMES` map). Launching Ascent from the
Library navigates the WebView to `file:///android_asset/ascent.html` → `ERR_FILE_NOT_FOUND` →
a white Chromium error page with a magnifying-glass icon, no BOOTSTRAP, no focus ring, and no
on-screen way out other than the remote's Back key.

### D-40 (S3) — No console pipe: JavaScript errors are invisible

**Evidence.** The `WebChromeClient` at `:125-128` overrides `onJsAlert` and `onJsConfirm` only.
`onConsoleMessage` is not overridden, and `WebView.setWebContentsDebuggingEnabled` is never called.

**Consequence.** Every error in 13 HTML pages and 9 shared scripts — plus every error thrown inside
the BOOTSTRAP, which wraps almost every statement in `try{…}catch(e){}` and swallows it — is
invisible in `logcat`. This is why divergences like the v1.6 `calLo()` bug can ship: nothing reports
them.

## 3.8 Injected-bootstrap defects (shell-side)

### D-41 (S1) — First D-pad press in a game lands on "Back"; the next OK exits the game

**Evidence.** BOOTSTRAP `:646`
`if(!cur||list.indexOf(cur)<0){ setFocus(list[0]); return; }` combined with the selector at `:640`
including `.iconbtn` and `[onclick]`, and `nova.html:65`:

```html
<button class="iconbtn" onclick="history.length>1?history.back():location.href='index.html'" aria-label="Back">&lsaquo;</button>
```

which is the **first** matching element in document order in every game. Unlike `x3f-nav.js`, the
BOOTSTRAP has no `data-nav-first` concept (`x3f-nav.js:114-118`).

**Failure scenario.** Player is mid-run in Nova and nudges the D-pad. Nothing appears to move except
a focus ring landing on the tiny `‹` in the top-left. They press OK expecting to dismiss the ring →
`history.back()` → the run is over.

### D-42 (S2) — The TV button is only hidden in three of the seven games that have one

**Evidence.** BOOTSTRAP `:590` injects `.tvbtn{display:none!important}`. The class is present in
`bloom.html:61`, `nova.html:66`, `splash.html:63` only. In `arena.html:89`, `duel.html:45`,
`flow.html:49`, `rhythm.html:45` the same button is written with **inline styles and no class**:

```html
<button onclick="x3tv()" aria-label="TV mode" style="display:inline-flex;…">TV</button>
```

**Failure scenario.** In Arena, Duel, Flow and Rhythm the dead "TV" button is visible, is picked up
by the BOOTSTRAP's `[onclick]` selector (`:640`), sits in the D-pad path, and when pressed calls
`x3tv()` (e.g. `arena.html:270`) which asks for fullscreen and an orientation lock inside a WebView
that is already both — i.e. it does nothing. The comment at `:587-589` says this button "lies";
it still lies in four games.

### D-43 (S2) — The BOOTSTRAP is injected into the three menu pages, where it duplicates and fights their own styling

**Evidence.** `:138` injects on any non-launcher `file:` URL. `routine.html`, `library.html` and
`progress.html` are non-launcher `file:` URLs, and `tools/sync-from-web.py`'s `TV_BLOCK` already
gives them a `@media (min-width:1200px)` block.

**Consequences.**
* `progress.html` has 9 elements with `class="card"`, so the BOOTSTRAP's
  `.card h1{font-size:38px!important} .card p{font-size:17px!important} .card .tag{font-size:14px!important}`
  (`:605-606`) applies there and competes with the page's own scaling. Both use `!important`;
  the later stylesheet wins, which is the BOOTSTRAP's — the game rules override the menu's.
* `select{font-size:15px!important;padding:11px 14px!important}` (`:599`) overrides
  `TV_BLOCK`'s `select{font-size:14px!important}`.
* A 62.5 Hz `setInterval` (`:617`) runs forever on pages with no `force` variable, creating
  `window.force` and burning a timer tick 62 times a second for nothing.
* `baseline=0` (`:583`) creates a stray `window.baseline` global.
* `.x3f-focus` CSS is injected on pages that use `x3f-nav.js`'s own ring — two ring definitions,
  only one used.

### D-44 (S3) — The `zeroBtn` capture listener is re-added on every `onPageFinished`

**Evidence.** `:624` has no idempotence guard, unlike the CSS (`:584 if(!st)`), the driver
(`:616 if(window.__x3fDrv)clearInterval`) and the nav (`:626 if(!window.__x3fNav)`).

**Consequence.** `onPageFinished` can fire more than once for a document (redirects, some
same-document navigations). Each fire adds another listener, so `X3F.reZero()` is called N times per
press. Idempotent today, but it is an unbounded listener leak in a file whose other three
injections are all carefully guarded.

### D-45 (S3) — `scope()` picks the last overlay in DOM order, not the topmost by stacking

**Evidence.** `:628`
`function scope(){ var m=document.querySelectorAll('.scrim.show,.modal.show'); if(m&&m.length)return m[m.length-1]; return document; }`
compared with `x3f-nav.js:61-65`, which additionally requires `boxed(el)` (non-zero size, not
`display:none`/`visibility:hidden`, opacity ≥ 0.05).

**Failure scenario.** A page that leaves `.show` on a faded-out overlay while opening a second one
earlier in the DOM traps the cursor in the invisible one. `x3f-nav.js` guards against exactly this;
the BOOTSTRAP does not.

### D-46 (S3) — The BOOTSTRAP nav cannot scroll

**Evidence.** `x3f-nav.js:152` `if (!best && (dir === 'up' || dir === 'down') && scrollPage(dir)) return;`
has no counterpart in the BOOTSTRAP (`:644-660`); the fallback there is only
`if(best)setFocus(best);`.

**Consequence.** A game overlay taller than the viewport (Nova's Upgrade Bay with many items) can
have controls the remote can reach only via `scrollIntoView` side effects, and nothing at all if the
last item in the direction is already focused.

# 4. WebView settings that are NOT set but should be

The shell sets exactly three `WebSettings` properties (`:120-122`) plus a background colour. Below is
every setting/override that a TV WebView shell of this shape should carry, with the concrete reason.

## 4.1 Performance and TV correctness

| Not set | Recommended | Why it matters here |
|---|---|---|
| `ws.setTextZoom(int)` | `100` | The system font-scale / display-size setting on Google TV multiplies WebView text. The whole UI is tuned in `vh` and fixed `px` (`launcher.html:25-84`, BOOTSTRAP `:595-607`); a user with "Large" text gets clipped chips and overflowing cards. |
| `ws.setUseWideViewPort(boolean)` | `true` | Without it the `<meta name="viewport" content="width=device-width, initial-scale=1, viewport-fit=cover">` on every page (`launcher.html:8`) is partly ignored — `initial-scale` and `viewport-fit` have no effect. Makes the CSS-pixel viewport explicit instead of density-dependent. |
| `ws.setLoadWithOverviewMode(boolean)` | `true` (with the above) | Pairs with `setUseWideViewPort` so a page wider than the viewport is scaled to fit rather than clipped. |
| `ws.setLayoutAlgorithm(...)` | `LayoutAlgorithm.NORMAL` | Guarantees `TEXT_AUTOSIZING` is off. Autosizing inflates text on large viewports — precisely the wrong thing when the BOOTSTRAP is already doing a deliberate 10-foot pass. |
| `ws.setCacheMode(int)` | `LOAD_CACHE_ELSE_NETWORK` | The only real fix short of removing the Google Fonts dependency (D-36): after one online run, the fonts come from cache and the app starts offline. |
| `ws.setBlockNetworkLoads(boolean)` | `true` once fonts are bundled | Turns D-36 from "hangs for seconds" into "fails instantly", and closes D-27 completely: no page in the WebView can reach the network at all. |
| `ws.setSafeBrowsingEnabled(boolean)` | `false` (API 26+) plus the `android.webkit.WebView.EnableSafeBrowsing=false` manifest meta-data | Safe Browsing initialisation costs real milliseconds at WebView startup and does periodic network work, all of it pointless for a `file://` bundle. |
| `ws.setOffscreenPreRaster(boolean)` | measure, then `true` (API 23+) | Keeps the WebView's tiles rastered when it is not the front window; removes the blank-then-paint on returning from a game. Costs memory — measure on the target TV first. |
| `ws.setForceDark(FORCE_DARK_OFF)` / `WebSettingsCompat.setAlgorithmicDarkeningAllowed(false)` | off | The theme is `Theme.DeviceDefault.NoActionBar` (`AndroidManifest.xml:29`), which is light on many OEM builds; WebView's algorithmic darkening can then invert an already-dark page and wash out the whole palette. |
| `ws.setMediaPlaybackRequiresUserGesture(false)` | **already set** (`:122`) | Correct — `x3f-music.js` needs it. |
| `ws.setDomStorageEnabled(true)` | **already set** (`:121`) | Load-bearing: all 12 `x3f_*` keys. |
| `web.setOverScrollMode(View.OVER_SCROLL_NEVER)` | set | Kills the stretch/glow at the ends of a D-pad scroll on the long Progress page. |
| `web.setVerticalScrollBarEnabled(false)` / `setHorizontalScrollBarEnabled(false)` | set | Scrollbars flash over the 10-foot UI on every remote scroll. |
| `web.setScrollBarStyle(View.SCROLLBARS_INSIDE_OVERLAY)` | set | Belt and braces with the above. |
| `web.setLongClickable(false)`, `web.setHapticFeedbackEnabled(false)` | set | Removes the text-selection/context path that a remote can trigger by accident. |
| `ws.setDisabledActionModeMenuItems(MENU_ITEM_NONE)` | set (API 24+) | Stops the floating Copy/Share action bar appearing over a game. |
| `web.setRendererPriorityPolicy(RENDERER_PRIORITY_IMPORTANT, false)` | set (API 26+) | On a 1 GB TV stick this is what stops the renderer being the first thing reaped. Pairs with the D-38 fix. |
| `getWindow().setSustainedPerformanceMode(true)` | set (API 24+) | Long canvas sessions thermally throttle. This asks for a stable clock instead of a boost-then-collapse curve. |
| `ws.setNeedInitialFocus(false)` | set | Stops the WebView auto-focusing the first focusable element on load, which fights the BOOTSTRAP's and `x3f-nav.js`'s own cursor models and is a contributor to D-41. |
| `web.setFocusable(true)` / `setFocusableInTouchMode(true)` | set explicitly | The WebView is the only view; making its focusability explicit removes an OEM variable. |
| `ws.setSupportZoom(false)`, `setBuiltInZoomControls(false)`, `setDisplayZoomControls(false)` | set | No touchscreen on TV, but a connected mouse or a phone-shaped device running the same APK can pinch/scroll-zoom out of the layout. |
| `ws.setDefaultTextEncodingName("utf-8")` | set | The pages are UTF-8 (`launcher.html:7`) and use `…`, `🔋`, `⟳` in native-injected strings (`:87`, `:531`). Explicit beats inherited. |
| `WebView.setWebContentsDebuggingEnabled(BuildConfig.DEBUG)` | set | Explicit remote debugging instead of relying on the shipped build happening to be `debuggable`. |
| `web.setInitialScale(...)` | leave unset, but decide deliberately | Currently implicit and density-dependent. |

## 4.3 Security-relevant settings left at their defaults

These are currently *safe by default* on `targetSdk 34`, but leaving them implicit is a landmine
because the defaults are version-dependent and the shell is a `file://` app with a Java bridge:

* `ws.setAllowFileAccess(...)` — default `false` on API ≥ 30, `true` below. `file:///android_asset`
  and `file:///android_res` remain readable either way, which is why the app works; make it
  `false` explicitly and document that assets are unaffected.
* `ws.setAllowContentAccess(false)`
* `ws.setAllowFileAccessFromFileURLs(false)` and `setAllowUniversalAccessFromFileURLs(false)` —
  default `false` since API 16, and the bundle relies on that default: **no page may ever use
  `fetch()`/`XHR` for a sibling file.** Every shared script is loaded with `<script src>` for this
  reason.
* `ws.setJavaScriptCanOpenWindowsAutomatically(false)`, `setSupportMultipleWindows(false)`
* `ws.setGeolocationEnabled(false)`, `setSaveFormData(false)`

## 4.4 Manifest / theme gaps

* No custom theme; no `android:windowBackground` matching `#05030F` (D-37).
* `android:configChanges` missing `uiMode|density|fontScale|smallestScreenSize|screenLayout|colorMode` (D-16).
* No `android:largeHeap="true"` — the games are full-screen canvases with `aurora.jpg`,
  `badge-*.jpg`, `bloom/bg.jpg` decoded into memory on a device that may have a 1 GB heap ceiling.
* `android:allowBackup="true"` with no `android:fullBackupContent` / `android:dataExtractionRules`:
  the WebView's `localStorage` (all training history) and the `x3f` prefs (`lastBar` MAC) are
  auto-backed-up to the user's Google account, and restored onto a different TV — including a bar
  MAC that does not exist there.
* No `android:banner` on the `<activity>` (only on `<application>`, `:26`).
* `android.hardware.bluetooth_le` `required="true"` (`:5`) blocks install on any TV without BLE,
  including emulators used for UI work.

# 5. Divergence between the injected bootstrap and the web build

The governing rule, stated in the code itself (`MainActivity.java:609-615`):

> *"This assignment REPLACES the browser build's onSample(), so anything that conditions the raw
> signal has to be repeated here or it silently does not exist on the TV."*

Here is the full audit of what `onSample()` does per game versus what the BOOTSTRAP driver does.

**BOOTSTRAP driver (`:617-621`):**

```javascript
var f=+window.__x3fForce||0;
if(typeof calLo==='function'){ var lo=+calLo()||0; f=f>lo?f-lo:0; }
force=f;
```

| splash | `:161` same | tare `:159` | floor ✅ · tare ❌ |
| flow | `:128` same | tare `:126` | floor ✅ · tare ❌ |
| duel | `:115` same | tare `:114` | floor ✅ · tare ❌ |

## DIV-01 (S1) — Arena's unit calibration is silently ignored on TV

`arena.html:200` multiplies by `scale`, the factor produced by "hang a known weight and capture"
(`arena.html:210`) and persisted as `store.set('scale', …)`. The BOOTSTRAP driver never applies it.

**Failure scenario.** The user calibrates Arena in the phone browser so the meter reads pounds
(`unit = 'lb'`). On the TV, the same `x3f_*` values are in the same origin's localStorage, the unit
label still says "lb" (`arena.html:242` `$('mUnit').textContent=unit`), and the number next to it is
in raw bar units. Two devices, same stored calibration, different numbers, no warning.

## DIV-02 (S1) — Bloom's per-set peak stays 0 on TV, so auto-calibration never learns

`bloom.html:160` is the *only* place `setPeak` is updated. The BOOTSTRAP does not update it, so
`bloom.html:283` / `:302` report `peak: Math.round(setPeak)` = `0`, and
`x3f-set.js:146` — `if (window.X3FCal && entry.ex && entry.peak > 0) X3FCal.observe(...)` — never
fires.

**Failure scenario.** A user who only ever plays on the TV never auto-learns a ceiling for any
movement. `X3FCal.range()` keeps returning the band default (`x3f-cal.js:104`, `auto:true`), so
every uncalibrated movement is scaled to the generic band max forever, and the PB tables and
"improvement" lines from `x3f-set.js` all see a peak of 0.

## DIV-03 (S2) — Arena's `sessionPeak` stays 0 on TV

`arena.html:201`. Consequences on TV: the Meter mode's "Peak" readout (`arena.html:242`) is always 0,
and "Capture band max" (`arena.html:230`, `if(sessionPeak>10){bandMax[band]=Math.round(sessionPeak)…}`)
silently does nothing.

## DIV-04 (S2) — The tare state machine does not exist on TV

Every game's `onSample()` starts with the `taring` branch. On TV, `onSample()` is never called, so:
* `taring` can never become `false` once set;
* `setStatus(demo?'Demo':'Live','on')` is never reached, so every game's status chip shows its
  initial value (`nova.html:68` `<span id="statusTxt">Offline</span>`) for the whole session even
  though the bar is live;
* `connected` and `demo` both stay `false` in every game.

The BOOTSTRAP's `zeroBtn` capture shim (`:624`) is what keeps this from being fatal — it stops
`startTare()` running (verified experimentally, see §2). **That shim is the only thing standing
between the current design and a permanently-stuck "Zeroing - hold still".**

## DIV-05 (S2) — Re-Zero means two different things

Web: `startTare()` averages a 1.5 s window after a 400 ms settle (`nova.html:160`).
TV: `X3F.reZero()` sets `haveBaseline=false` (`:427`) and the very next BLE packet becomes the
baseline (`:348`). A single noisy sample versus a 1.5 s mean. Same button, different statistics,
different stored floor semantics against `x3f-cal.js`'s `lo`.

## DIV-06 (S2) — `window.__x3fNative` is false on the launcher and the menu pages' first paint

`window.__x3fNative=true` is set by the BOOTSTRAP (`:582`), which is *not* injected on the launcher
(`:135-137`). `x3f-nav.js:91` uses it:

```javascript
if (!cursor && items.length && (engaged || window.__x3fNative)) { justScoped = true; setCursor(first()); }
```

So on the launcher, an overlay that opens before the user's first D-pad press does not get the
cursor. Any future code that branches on "am I on the TV?" will get the wrong answer on the launcher.

# 6. Design weaknesses and opportunities, ranked

**1. The force transport is the wrong mechanism.** 62 `evaluateJavascript` calls per second
(`:355-356`), each a JNI hop, a task posted to the UI thread, and a full V8 script compile+eval of a
fresh source string, feeding a **separate** 16 ms `setInterval` in the page (`:617`) that samples
whatever happens to be there. Two unsynchronised clocks means beat-frequency jitter on the value the
game reads, on top of the dropped-peak problem (D-06). Replace with either (a) a
`@JavascriptInterface double force()` pulled from the game's own `requestAnimationFrame`, or (b)
`WebViewCompat.postWebMessage` / a `WebMessagePort` pair with a small binary payload. Either removes
the string-eval cost entirely and lets the page sample in phase with its own frame.

**2. Lifecycle is unimplemented.** No `onPause`/`onResume`, no `web.onPause()`/`pauseTimers()`, no
scan suspension, no GATT release, no state save. This is the root of D-15, D-16, D-19 and half of the
battery/CPU story. It is also the smallest, highest-value patch in the file.

**3. The whole shell is one 669-line class with no seams.** BLE, WebView hosting, key handling, the
updater and an 88-line JavaScript program all share one set of mutable fields and four threads. There
is no `BarConnection` type, no `ShellBridge` type, no state enum, and no unit tests (the project has
none at all). A refactor should extract: `BleBar` (connection state machine, single-threaded on one
`HandlerThread`), `WebHost` (WebView + settings + clients), `Updater`, `RemoteKeys`, and move the
BOOTSTRAP into an asset file.

**4. The BOOTSTRAP should be an asset, not a Java string.** As a `.js` file under `assets/` it would
get syntax highlighting, `node --check` in CI, a diffable history, and — most importantly — the
option of being `<script src="x3f-shell.js">` in the pages themselves, which removes the entire
"injected at `onPageFinished`" timing class of bug. The two test harnesses already treat it as a
file (they extract it and write `bootstrap.js`). The cost is that
`tools/nav-audit/run.py:79` and `tools/func-test/run.py:122` must be updated in the same commit.

**5. The `onSample()` / BOOTSTRAP divergence is structural, not a series of bugs.** Three times now
(v0.9 `vis()`, v1.6 `calLo()`, and today's DIV-01/02/03) the same shape of bug has shipped. The fix is
to make the games expose **one function** — e.g. `window.__x3fIngest(rawForce)` — that the browser's
BLE handler and the shell both call, so `onSample()`'s conditioning is the only implementation. Then
the BOOTSTRAP shrinks to `window.__x3fIngest(f)` and no future conditioning can be missed. This
single change retires the entire divergence category and makes `func-test`'s `bloomtv` scenario a
guard rather than a canary.

**6. Bundle the fonts.** Two font families across 13 pages, fetched from the network at every page
load, in an app whose value proposition is "turn on TV → play". Subsetted woff2 for Fredoka + Space
Grotesk + Sora is well under 200 KB. This is the largest single win in perceived startup time and it
also lets `setBlockNetworkLoads(true)` close D-27.

**7. Move the launcher off `file://` — but only with a migration.** `WebViewAssetLoader` serving
`https://appassets.androidplatform.net/` would give a real origin: service workers, `fetch()` for
local files, sane CORS, and a non-shared localStorage. **But that changes the storage origin and
orphans every `x3f_*` key.** If it is done, it must ship with a one-time migration that reads the
old `file://` localStorage (via a hidden `file://` page + `postMessage`, or by exporting through the
existing `x3f-progress.js` export/import path) before switching. See §7 INV-05.

**8. Replace hand-built JSON with `org.json`.** `pushDevices` (`:466-483`) concatenates strings and
`jsSafe` (`:461-465`) is a blocklist. `org.json.JSONArray`/`JSONObject` are in the framework, no
dependency needed, and they solve D-26's Java half correctly. Pair with `textContent` at the sink.

**9. The updater should verify what it downloaded.** Publish a SHA-256 alongside `version.txt`,
check it before launching the installer, and check
`PackageManager.getPackageArchiveInfo(...).versionCode == remote`. Also key the "is there an update"
question on something that actually changes when the assets change (git SHA or an asset-tree hash),
not on a manually-bumped `versionCode` (D-31).

**10. Give the shell a status/diagnostics surface.** `onConsoleMessage` → logcat, plus a hidden
diagnostics overlay (BLE state, last N packets, packet rate, injected value, WebView renderer
memory). Every defect in §3.1–3.2 is currently invisible from the couch and invisible in logcat.

**11. Ship a release build, not a debug build.** CI publishes `app-debug.apk`. Switch to
`assembleRelease` (which is already configured with the same signing config, so in-place updates keep
working), and add `WebView.setWebContentsDebuggingEnabled(BuildConfig.DEBUG)` so debugging is an
explicit choice rather than a side effect of the build type.

**12. Add a D-pad repeat policy.** Filter `getRepeatCount()`, add a ~350 ms initial delay and a
~120 ms repeat with a small acceleration — the numbers `x3f-nav.js:261-262` already uses for the
gamepad (`380` then `130`). Reuse them so the remote and a controller feel the same.

**13. Give the games a `data-nav-first`.** The BOOTSTRAP focuses `list[0]` (D-41). Either honour
`data-nav-first` the way `x3f-nav.js:116` does, or better: retire the BOOTSTRAP's private nav and
load `x3f-nav.js` in the games too. `HANDOFF.md` explains why that was avoided ("its Enter/Space
handling would fight Space-to-pull in the browser build") — which is solvable by gating the keydown
listener on `!window.__x3fNative`, and would collapse two nav implementations into one.

**14. Two launcher copies and a missing game page.** Make `sync-from-web.py` generate `index.html`
from `launcher.html` (or make `index.html` a one-line redirect), and either bundle `ascent.html` or
remove it from `X3FFILES`. Both are cheap and both are currently user-visible.

**15. Consider `androidx.webkit`.** `WebViewAssetLoader`, `WebViewFeature`,
`WebSettingsCompat.setAlgorithmicDarkeningAllowed`, `WebViewCompat.postWebMessage` and
`ProcessGlobalConfig` all live there. The "no third-party dependencies" stance
(`HANDOFF.md`) is costing real capability; AndroidX is already enabled in `gradle.properties`.

### INV-02 — The `X3F` bridge name and its five methods

`window.X3F.reZero()`, `.checkUpdate()`, `.pickDevice(addr)`, `.setOverlay(bool)`, `.rescan()`.

*Evidence:* bound at `:124` as the literal string `"X3F"`; called at `launcher.html:191, 237, 248, 255`
and BOOTSTRAP `:624`. `launcher.html:191` also uses the *absence* of `window.X3F` to print

### INV-03 — `setOverlay` must remain synchronous relative to the key event

*Evidence:* the comment at `:443-445` — *"evaluateJavascript is async, so the answer has to be here
before the key arrives"* — and `:554` reading `overlayOpen` inside `dispatchKeyEvent`. If overlay
state is ever queried by evaluating JS at key time instead of being pushed ahead of time, Back will
race and drop the app to the home screen from an open modal.

### INV-04 — The `zeroBtn` interception must stay capture-phase with `stopPropagation`

*Evidence:* BOOTSTRAP `:624`
`z.addEventListener('click',function(ev){ ev.preventDefault(); ev.stopPropagation(); … },true)`.
Verified experimentally: a capture listener on the target runs before the element's `onclick`
property handler and `stopPropagation()` suppresses it. Every game binds
`$('zeroBtn').onclick=()=>{if(demo){baseline=0}else startTare()}`
(`nova.html:173`, `splash.html:171`, `bloom.html:170`, `flow.html:138`, `duel.html:123`,
`rhythm.html:124`, `calibrate.html:153`, `arena.html:219`). If that handler ever runs on the TV,
`startTare()` sets `taring=true` and only `onSample()` — which never runs on the TV — can clear it:
every game wedges on "Zeroing - hold still" and its status chip never recovers.

### INV-05 — One shared `file://` localStorage origin for all bundled pages

*Evidence:* `LAUNCHER = "file:///android_asset/launcher.html"` (`:69`), `ws.setDomStorageEnabled(true)`
(`:121`), and cross-page state: `launcher.html:135-136` reads/writes `x3f_band` and `x3f_bandMax`
which `x3f-cal.js:78` and every game then read; `x3f-progress.js` derives everything from
`x3f_history`; `x3f-cal.js:22` keys on `x3f_exCal`; `routine.html` hands a session to the games via
`x3f_session` (`x3f-cal.js:90`). The full key set is:
`x3f_ach, x3f_band, x3f_bandMax, x3f_chal, x3f_cues, x3f_exCal, x3f_formOn, x3f_history, x3f_music,
x3f_prog, x3f_routine2, x3f_session`.
**Changing the WebView origin (to `https://appassets.androidplatform.net`, to a custom scheme, or by
calling `WebView.clearCache`/deleting the WebView data dir) destroys every user's entire training
history with no warning and no recovery path.** Any such move needs an explicit migration.

### INV-06 — Assets remain reachable as `file:///android_asset/*` and load with `<script src>`, never `fetch`

*Evidence:* `:69`, `:138` (`url.startsWith("file")` gates the BOOTSTRAP), the games' `<script
src="x3f-cal.js">` tags (`nova.html:60` etc.), and the fact that
`setAllowFileAccessFromFileURLs`/`setAllowUniversalAccessFromFileURLs` are left at their `false`

### INV-07 — Two nav owners, arbitrated by `if(!window.__x3fNav)`

*Evidence:* BOOTSTRAP `:626` `if(!window.__x3fNav){ … }` versus `x3f-nav.js:283-300`
`if (!window.__x3fNav) { window.__x3fPageNav = true; window.__x3fNav = function (dir) {…}; }`.
`x3f-nav.js` is loaded synchronously in the body of `launcher.html:93`, `index.html`, `library.html`,

`tools/nav-audit/audit.js:56` reads `window.__x3fPageNav` to report which nav is driving.

### INV-08 — Same-row/column overlap must dominate the spatial-nav score

*Evidence:* BOOTSTRAP `:653-658`
`var d=along+perp*2.5+(ov>2?0:4000);` and `x3f-nav.js:140-144`
`var score = fwd + cross * 2.2 + (overlap > 2 ? 0 : 4000);`. `HANDOFF.md` records the shipped bug
this fixed (v0.6: Right off Workout landed on a band pill). The `4000` penalty and the `>2px`
overlap threshold are the mechanism; the two implementations use different multipliers (2.5 vs 2.2),
which is itself a small divergence but the overlap rule is the invariant.

### INV-09 — Ancestor-walking visibility, not element-only

*Evidence:* BOOTSTRAP `:633-639` and `x3f-nav.js:40-46` both walk `parentElement` checking

### INV-10 — Overlay scoping traps the cursor

*Evidence:* BOOTSTRAP `:628` (`.scrim.show,.modal.show`) and `x3f-nav.js:53`
(`.coach.show,.rest.show,.scrim.show,.modal.show,[data-nav-scope]`).
`tools/nav-audit` fails on `ESCAPED OVERLAY`. The class-name contract — `.show` as the open marker,
`.scrim`/`.modal`/`.coach`/`.rest` as the overlay roots — is shared across 13 HTML files.

### INV-11 — The BOOTSTRAP must remain extractable by regex from `MainActivity.java`

*Evidence:* `tools/nav-audit/run.py:79` and `tools/func-test/run.py:122`, both
`re.search(r'BOOTSTRAP\s*=\s*"""(.*?)""";', java, re.S)`. Plus `tools/nav-audit/run.py:88` requires
the literal seam anchor `"   setInterval(function(){ try{ var sc=scope();"` — **three leading

`run.py:110` additionally hard-codes that the launcher and `index` are the two pages that do **not**

### INV-12 — Java text-block escaping rules inside BOOTSTRAP

*Evidence:* `:580-668`. The current content contains **no** `\` and no `"` — every JS string uses
single quotes. In a text block a lone `\` is an escape and `"""` terminates the block. Any future
edit that introduces a backslash (a regex, `\n`, a Windows path) must double it, and the resulting
JS will then differ from what a reader sees. The closing `"""` at column 0 (`:668`) is also what
keeps incidental-whitespace stripping at zero; indenting the whole block changes the extracted
string.

### INV-13 — The `calLo()` contract, including Calibrate's deliberate absence

*Evidence:* BOOTSTRAP `:619` `if(typeof calLo==='function'){ var lo=+calLo()||0; f=f>lo?f-lo:0; }`,
the comment at `:609-615`, `calLo()` defined in seven games
(`arena.html:173`, `bloom.html:119`, `duel.html:90`, `flow.html:96`, `nova.html:129`,
`rhythm.html:91`, `splash.html:121`) and **not** in `calibrate.html` (which still loads
`x3f-cal.js` at `:49`). `tools/func-test/cases.js:178-201` is a mutation-verified regression test:
